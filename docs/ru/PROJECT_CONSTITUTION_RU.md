# Конституция проекта XCEasy

Статус: действующий нормативный документ. Версия: 2.0. Дата изменения: 9 сентября 2026 года.

## 1. Миссия

XCEasy делает iOS UI-тесты предсказуемыми, читаемыми и диагностируемыми. Фреймворк должен сокращать стоимость создания и поддержки тестов, сохраняя XCTest/XCUI как исполняемую основу. Особое требование — пригодность к безопасной доработке и диагностике ИИ-агентами.

## 2. Обязательные принципы

### I. Достоверность важнее удобства

Фреймворк не должен скрывать неоднозначный selector, потерянный artifact, telemetry failure или неуспешное ожидание. Convenience API допустим только при сохранении первичной причины, expected/actual и контекста выполнения.

### II. Диагностируемость является функциональностью

Каждая операция, способная завершить тест ошибкой, должна оставлять структурированные доказательства: тип операции, входы после redaction, результат, duration, source location и correlation IDs. Логи и diagnostic bundle тестируются как публичный контракт.

### III. Безопасность по умолчанию

Защищайте инфраструктурные секреты и сохраняйте точечную фильтрацию учётных данных до текстовых sinks. Дерево UI, значения полей, скриншоты и явный debug output помогают диагностике и могут содержать данные приложения; не маскируйте их целиком и не отключайте без явного требования пользователя. Существующий фильтр работает по ограниченным правилам и не гарантирует обезличивание. Используйте синтетические аккаунты и управляйте доступом/хранением артефактов. Новое текстовое логирование учётных данных требует проверок конкретных правил; raw HTTP headers/body по-прежнему не логируются. См. [ADR 0021](adr/0021-diagnostic-privacy-boundary.md).

### IV. Детерминированность и изоляция

Тесты не зависят от порядка, глобального изменяемого состояния другого теста или абсолютных локальных путей. Параллельный запуск является проектным ограничением. Общий mutable singleton требует явного обоснования, синхронизации и concurrency tests.

### V. Совместимость и эволюция

Public Swift API, telemetry schema и artifact layout версионируются. Breaking change требует migration guide и major version либо заранее утверждённого deprecation cycle. Добавление public API требует документации и тестов.

### VI. Evidence-driven changes

Исправление дефекта начинается с воспроизведения и заканчивается regression test. Новая функция должна иметь проверяемые acceptance criteria. Утверждения о build, performance, thread safety и compatibility допустимы только с воспроизводимым подтверждением.

### VII. Простая архитектура

Предпочитаются маленькие типы, явные зависимости и один источник истины. Новая абстракция должна уменьшать связность или дублирование. Allure является adapter-ом, а не владельцем всей доменной модели диагностики.

### VIII. AI-ready, human-readable

Канонические данные машинно-читаемы и стабильны; человек получает понятное представление тех же данных. ИИ не должен угадывать смысл по локализованной строке. Автоматический патч обязан ссылаться на evidence и проходить те же проверки, что человеческий.

### IX. Production и release readiness

Поддерживаемая возможность должна иметь зафиксированную environment matrix, public documentation, compatibility contract, release metadata и воспроизводимый quality gate. Наличие кода без этих условий не означает production support. `release-metadata.json.version` является единым источником версии; tag, changelog и API baseline обязаны ему соответствовать.

## 3. Definition of Done

Изменение готово, только если:

- выполнены acceptance criteria;
- добавлены/обновлены тесты нужного уровня;
- public behavior и документация синхронизированы;
- RU/EN пользовательские примеры соответствуют фактическому public API;
- новые failure paths диагностируемы;
- privacy/redaction проверены;
- нет machine-specific paths и случайных generated artifacts;
- build/test/lint-команды выполнены либо ограничение явно зафиксировано;
- breaking changes, риски и migration описаны.
- release metadata и API compatibility проверены, если изменение входит в поставку.

## 4. Запрещённые практики

- `fatalError`, force unwrap и silent `try?` на пользовательском execution path без доказанной невозможности ошибки;
- логирование credentials или полного необработанного network body;
- исправление теста простым увеличением timeout без анализа причины;
- selectors по index/text, если доступен стабильный identifier;
- удаление/ослабление теста только ради зелёного CI;
- изменение public API или event schema без compatibility analysis;
- ручное редактирование generated файлов;
- заявление «поддерживается» без CI-проверки соответствующей матрицы.
- дублирующие источники версии, схемы или release status, способные разойтись.

## 5. Управление решениями

Существенное решение фиксируется ADR в `docs/adr/NNNN-title.md`: контекст, варианты, решение, последствия и статус. ADR обязателен для новых модулей/зависимостей, concurrency model, telemetry schema, distribution, breaking API и security/privacy policy.

Приоритет документов: Конституция → утверждённая спецификация/ADR → code style → contribution/AI guides → README. Исключение должно быть локальным, объяснённым в PR и, если принципиально, оформленным поправкой.

## 6. Изменение конституции

Поправка требует отдельного review, описания мотивации и migration impact. Версия увеличивается: major при изменении принципа, minor при добавлении правила, patch при уточнении без изменения смысла. История поправок сохраняется внизу документа.
